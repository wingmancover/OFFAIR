# OFFAIR 蓝图与 C++ 技术路线

本轮技术结论：当前 [GM 原型](../design/gm-prototype.md)采用纯蓝图合适，暂不引入 C++。这是针对现有规模的工程选择，不将“最终项目必须纯蓝图”设为限制；出现明确的维护、测试、引擎接口或性能需求时，再迁移少量核心逻辑。

## 为什么当前选蓝图

当前主要操作是死亡、阶段切换、少量敌人增删和单台监控控制。它们以事件触发为主，重建世界、生成对象和切换视角的成本也不能简单等同于蓝图脚本的执行成本。仓库已有蓝图模板，目前没有测得脚本性能瓶颈，因此没有依据为了性能预先增加原生模块。

Epic 将蓝图的快速原型迭代列为优势，并指出 C++ 的性能收益取决于实际场景；出现性能问题时应先分析主要瓶颈，再决定是否迁移。这支持本项目先做可测量的蓝图原型，而非证明所有未来场景都适合蓝图。[官方蓝图与 C++ 对比](https://dev.epicgames.com/documentation/en-us/unreal-engine/coding-in-unreal-engine-blueprint-vs-cplusplus)

蓝图适合事件驱动逻辑；大量实例逐帧执行复杂计算时才更需要评估原生实现。当前应先减少无意义的逐帧查询和重复状态判断，按事件更新阶段和面板。监控实时转向仍可按输入更新，不因“避免 Tick”而破坏必要的连续控制。[官方蓝图最佳实践](https://dev.epicgames.com/documentation/en-us/unreal-engine/blueprint-best-practices-in-unreal-engine)

引入 C++ 需要团队维护编译工具链、原生模块及其与蓝图资产的接口。对当前六个主按钮及背后的小型系统，这项成本尚无明确收益。纯蓝图同样需要清晰的数据、状态与职责划分；选择蓝图不意味着把全部逻辑塞进关卡蓝图或界面事件。

## 当前职责划分

以下名称为建议，并非已经创建的资产。根据实际图规模可以合并小型职责，不为每个动作强行增加一个类。

| 部分 | 蓝图承载方式 | 主要职责 |
| --- | --- | --- |
| GM 界面 | `WBP_GMPanel` | 六个主按钮、设备选择、只读状态与结果；不直接改阶段和敌人数 |
| GM 调度 | PlayerController 上的专用组件或独立蓝图对象 | 统一校验和分派命令、处理面板焦点；正式玩法不依赖 GM 面板存在 |
| 会话与阶段 | GameInstance 保存会话进度，GameMode 或阶段管理对象执行重建 | 当前／待生效／目标阶段分开，防重复重置、失败恢复与新旧尝试隔离 |
| 阶段数据 | 蓝图结构体配合配置资产或数据表 | 阶段顺序、出生点、敌人初始数量及监控初始状态 |
| 敌人生成 | 专用生成管理对象，复用已验证 NPC 模板 | 生成点、实例登记、数量上限、移除清理与重置 |
| 监控 | 监控 Actor 与 PlayerController | 转向、视角、输入、正常退出与异常中断 |

首版入口采用运行时 UMG 调试面板。Widget Blueprint 可以布局界面并实现脚本交互，不需要为了几个按钮先增加原生控制台支持。[官方 UMG 入门](https://dev.epicgames.com/documentation/en-us/unreal-engine/umg-ui-designer-quick-start-guide-in-unreal-engine)

地图重置先采用重载后应用目标阶段配置；测试加载等待及初始化可靠性后再决定是否改为原地恢复。改用 C++ 与改用原地重置是两个独立选择，C++ 本身不会自动缩短地图加载时间。

## 何时值得引入 C++

| 实际触发条件 | 优先迁移的部分 | 仍适合留在蓝图的部分 |
| --- | --- | --- |
| 阶段条件、分支和保存逻辑持续扩展，核心图已难以审阅 | 阶段状态模型、条件结算、重置协调 | 关卡配置、事件编排与演出 |
| 需要独立于地图执行大量自动化边界测试 | 纯状态转换和条件判定 | 场景集成与实际镜头验证 |
| 多人频繁修改相同核心资产，需要可靠的文本 diff 和合并 | 多人共同维护的核心类型与接口 | 各自负责的关卡和表现资产 |
| 性能分析确实定位到大量 AI 或密集蓝图计算 | 已测得的热点算法或批量处理 | 单体行为调参、动画和 UI |
| 需要蓝图未暴露的引擎能力或稳定的原生控制台入口 | 小型原生接口与命令适配层 | 已有玩法逻辑和面板 |

C++ 的文本存储更便于 diff 和合并；Epic 也提供蓝图 Diff 工具，所以不能把蓝图说成完全不能审阅。对 Codex 协作而言，当前会话可直接检查文本，尚未验证可编辑蓝图图表的 Unreal 工具连接；这会影响实际实现方式。该工具限制不是游戏必须使用 C++ 的理由，实现蓝图前需落实编辑器操作或可靠自动化通道。[官方对比与协作说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/coding-in-unreal-engine-blueprint-vs-cplusplus)

如果以后明确需要在 Unreal 原生控制台输入带参数的命令，可评估薄层 C++ `UFUNCTION(Exec)` 入口，再调用同一套游戏能力。`Exec` 只在特定类中生效；`BlueprintCallable` 只是蓝图可调用，并不等于注册了控制台命令。当前 GM 动作名不会被描述成现成控制台语法。[官方 UFunctions 说明](https://dev.epicgames.com/documentation/unreal-engine/ufunctions-in-unreal-engine?lang=en-US)

## 为后续迁移保留的边界

GM 层只提出死亡、切阶段、增减敌人和连接监控的请求；世界与玩法系统负责执行。关键阶段数据不要由 UI 直接修改；对象按稳定标识登记，避免每次操作扫描整个世界或重复绑定事件。

如果后续迁移，优先把稳定规则放到可向蓝图暴露的 C++ 基类或组件，保留关卡参数、UI 和表现资产。迁移需要调整引用并重新测试，不承诺一键无成本转换。每次迁移应由明确问题驱动，不同时重写所有模板与地图。

当前不新增 `Source/`、原生模块、插件或工具链要求。本轮只更新技术方案；后续首个实现迭代需实际编译蓝图、运行 GM 用例，并记录测试地图与结果。
