## 建议职责划分

当前用少量职责明确的蓝图组成闭环，不为原型预建大型通用框架。GM 面板与底层能力分离，实际交互后续再接入。确有测试、复杂度或性能收益时再加入 C++，见 D-13。

| 职责 | 建议载体 | 对外能力与边界 |
| --- | --- | --- |
| GM 操作入口 | UMG 面板与 PlayerController 上的调度组件或等价对象 | 分派死亡、相邻阶段跳转、敌人增减与连接监控；不在 Widget 中直接维护世界状态 |
| 会话阶段进度 | 项目专用 GameInstance 或等价会话容器 | 保存当前、待生效、重置目标阶段和运行标识；重载时不依赖旧 Actor 引用 |
| 循环流程管理 | GameMode 或独立管理对象 | 接受玩法事件、判定条件、处理一次死亡、应用初始状态；仅此处决定阶段推进 |
| 阶段定义 | 数据资产、数据表或明确的配置结构 | 描述阶段初始状态和条件，不保存上一轮运行时对象 |
| 玩家控制与监控视角 | PlayerController 与角色相关组件 | 当前接 GM 入口，维护本体与监控控制状态，统一退出、死亡与阶段跳转清理 |
| 监控设备 | 专用监控 Actor | 提供设备视角、受限旋转、覆盖与侦测状态，不自行重载关卡 |
| 敌人管理 | 生成管理对象与已检查 NPC 模板 | 登记、增减、初始化 AI 和重置数量；GM 移除不计为击杀 |
| 后续武器、门与物品 | 正式交互版本再适配模板 | 当前不新增拾取、掉落、终端或通关机制 |

会话容器负责保留少量进度；当前世界对象负责执行行为。避免把所有玩法都放进 GameInstance，或让每个 Actor 自行解释“下一阶段”。

### 最小事件约定

建议事件至少包含 `EventType`、`TargetId`、`StageId`、`RunId`；进入管理者后记录处理序号。完整玩法的事件类型包括 `ItemAcquired`、`EnemyKilled` 和 `PlayerDied`；黑入或通路通过事件按后续关卡需要添加。

当前先接实际 `PlayerDied` 和 GM 请求。物品／击杀条件可以通过内部测试夹具注入验证，实际交互后续接入；GM 跳阶段与移除敌人使用独立调试原因，不冒充上述正式事件。

目标标识在编辑配置时分配，不能依赖重载后会变化的显示名、对象地址或生成序号。管理者校验当前运行状态、目标与阶段，拒绝旧尝试和重复事件。进入初始化流程时先关闭事件接受，避免物品重建或敌人初始化被当成玩家已完成目标。

## 世界重置方案建议

首版建议在同一张原型地图上采用“重载地图，再应用目标阶段配置”的方案。它更容易检查旧对象是否清空，但必须实测加载耗时、外部 Actor 加载完整性、会话进度保留和初始化顺序，不能把重载完成自动视为整个阶段已就绪。

方案需要的约束：

1. 重载前在会话容器固定目标阶段和待提交进度，不保存旧世界 Actor 指针。
2. 新世界初始化由一个入口协调；关闭输入、AI 与条件监听，待必需对象与出生点就绪后统一启用。
3. 基础地图提供静态布局，阶段配置决定哪些敌人、物品、门与监控存在及其起始状态。明确每类对象由地图放置还是运行时生成，不能两边都生成。
4. 新世界全部验证成功后提交阶段变化。加载或配置失败时保留重试目标，进入可恢复界面，不退回已经完成的旧进度。
5. 调试记录区分阶段、尝试与重置操作；验证旧延迟任务、投射物或外部回调无法影响新世界。

若实测重载等待破坏循环节奏，再评估“对象注册表 + 重置接口”的原地重置方案。原地重置必须完整处理已销毁对象重建、临时对象清理、AI、物理、计时器和输入恢复；无需为了未来可能优化而同时维护两套重置路径。

当前选用这条路线作为 GM 原型起点，待测量重试耗时后再评估是否调整；它不约束最终项目必须采用相同方案。

## 新增资产的建议组织

```text
Content/OFFAIR/
  Core/           阶段管理与阶段定义
  Debug/          GM 调度、测试配置与辅助对象
  AI/             敌人登记与生成管理
  Surveillance/   监控设备、转向与侦测
  Levels/         专用灰盒地图及阶段配置
  UI/             交互反馈、复活反馈与调试显示
```

这些目录尚未创建。优先引用或继承已验证模板；只有必要时才复制受修改资产，并记录引用关系。模板地图保留为对照，不直接在整个模板库上批量改名或迁移。

## 当前 GM 迭代与完成标准

按依赖推进，不在缺少团队人数和截止日期时编造工期。每次迭代按 [AGENTS.md](../../AGENTS.md) 检查、实现、验证、审阅并提交。

| 迭代 | 可演示成果 | 验证门槛 |
| --- | --- | --- |
| M0 范围与选型 | 五类 GM 定义、纯蓝图路线、实际交互暂缓清单 | 文档一致、链接有效；本次已落地 |
| M1 死亡与阶段切换 | GM 面板、两个可辨识的阶段初始状态、死亡及前后跳转 | G-01 至 G-05；先检查模板自动重生冲突 |
| M2 敌人管理 | 增减可运行 AI、数量与生命周期管理 | G-06 至 G-08；原有与 GM 增加的敌人都能正确恢复 |
| M3 监控控制 | 一键接入、真实转向、返回本体、死亡和跳阶段中断 | G-09 至 G-11；不依赖终端或道具 |
| M4 集成验证 | 在同一地图反复组合全部 GM 操作 | 完整执行 G-01 至 G-14；记录重复重置与异常恢复结果 |

当前不要求完成 T 系列的实际拾取、击杀掉落、权限终端、警报封路或整关通行。后续重新启动交互版本时，再将这些内容拆成独立迭代并启用相应 T 用例。

## 调试与演示准备

GM 面板显示当前阶段、待生效阶段、`RunId`、运行状态、实际敌人数、目标设备和最近结果。主操作限定为[五类 GM 功能](../design/gm-prototype.md)，另提供监控退出与面板开关等必要收尾。条件注入和初始化故障使用测试夹具，不扩展成一套复杂 GM 平台。

当前演示重现死亡重试、前后阶段恢复、敌人增减、监控进出与中断。使用 GM 跳转时明确标注调试操作；通过内部条件注入测试不等于真实拾取或击杀交互完成。报告或答辩材料应来自实际运行截图与记录，不用设计图替代完成证据。

每次涉及行为的验证记录应包含日期、提交版本、编辑器或构建环境、地图、初始阶段、操作步骤、期望与实际结果。日志和录屏按需保存，避免提交大型临时产物或本机缓存。若建立自动化入口，在实际跑通后补充到 README。

## 优先风险与应对

| 风险 | 实施时的应对 |
| --- | --- |
| 重置遗漏导致状态累积 | 建立可变对象清单；覆盖多轮循环，不只测试第一次复活 |
| 条件与死亡竞争导致错阶段 | 单一事件入口、明确事件顺序、重复及旧事件测试 |
| 监控退出后控制失效 | 所有中断走统一清理路径，覆盖死亡和目标销毁 |
| 模板重生或刷怪与循环冲突 | 编辑器检查模板逻辑，确定唯一的出生与生成职责 |
| 循环变成重复劳动 | 单个短战斗、缩短重试路径，试玩后决定是否拆出新阶段 |
| 摄像机转向只有视觉变化 | 对照默认与改向后的本体通行结果，检查遮挡和实际视锥 |
| 阶段配置漏配导致无法继续 | 初始化校验必需对象、关键物品可达性、死亡或重试入口 |
| 先扩充内容导致 GM 验证迟迟不成立 | 当前 M4 通过前不新增权限道具、终端、完整关卡或大型资产制作 |
